范围要求映射算法数据架构实施阶段验收团队与交付

1. 用户、业务问题与产品范围

分析师想知道：“如果我认为进攻方出现无得分回合的概率更低，胜率、最终分差和总分会怎样改变？这个模型在类似时间段的历史预测表现如何？我依据什么接受或拒绝这个假设？”平台把假设、计算结果、验证报告与审查决定关联起来。

这是面向 DraftKings 工作流的历史研究与模型审查原型。现有数据截至 2023 年，不能据此承诺 2026 年真实定价准确性；不接真实下注、不自动改赔率、不把参数敏感性称为球员伤病的因果效应。

建议页面用户做什么主要输出
Scenario Lab选择历史比赛与已验证的回合起点，查看当时状态；保存假设，运行基准与调整场景。胜率、分差与总分分布、差异、模拟次数、模型版本、支持样本数和不确定性说明。
Model Validation检查模型在未参与训练的比赛上的表现，按赛季、剩余时间和分差切片。校准图、Brier score、log loss、分差/总分误差与区间覆盖率；运行耗时和吞吐量。
Research & Review查询模型与历史实验报告，阅读来源；写审查意见，标为 Reviewed。带引用回答、证据链接、Open → Reviewed 状态和可追踪的审查记录。

原 Market Monitoring 作为独立扩展页保留规划，读取已有 h2h/moneyline 样本，显示报价时间；不在刷新时请求外部 API。2026 年赔率/新闻与旧比赛分开显示。Similar Game Finder 不属于本次 simulator 核心交付；本计划不删除已有采集代码或资料。

演示流程：历史比赛起点 → 查看基准 → 调低无得分回合概率 → 比较模拟分布 → 查看对应模型的验证报告 → 通过 RAG 找到适用限制 → 保存审查决定 → 刷新后仍可读取。

3. 数据与算法：先验证，再扩大

3.1 已有数据与缺口

2026-11-20 只读全表核对：13,592,899 条事件的 pctimestring 无 NULL/空字符串，period 和 eventnum 无 NULL。实际有时钟、事件类型、描述、比分更新与参与球员/球队，但没有现成的 possession_id、回合耗时或完整场上阵容列。字段非空不证明事件顺序、记录完整性和时钟正确。

已发现需要处理的情况：非得分事件的 score 大量为空；两条投篮命中事件没有 score；All-Star 样本有连续 0:00 事件；game 表样本存在重复 game_id；部分球队 ID 带字符串后缀 .0。先规范 ID、验证关联键、筛选比赛类型，并记录所有排除。NBA 全部比赛日期范围不能直接当作 play-by-play 覆盖范围。

3.2 回合数据契约

每条合格回合至少包含 game_id, possession_id, period, offense_team_id, defense_team_id, start_clock_seconds, start_score_offense, start_score_defense, start_type, duration_seconds, points_offense, points_defense, end_reason, source_event_ids, quality_flags。保留得分事件在回合内的相对时间及顺序，处理节末截断和罚球；原始事件只读保留。

初始状态来自起点当时已知的信息。训练样本的回合结果来自后续已结束事件；模拟启动后的状态由模拟结果更新。球队强度等特征只用此前比赛计算。普通节末与加时、0 秒事件、技术罚球、进攻篮板及多事件同时间必须有明确定义；异常回合不能静默当作 0 分。

3.3 建模方案与选择

  • 建议第一版：状态分组 + 平滑的条件联合经验分布 + Monte Carlo。按剩余时间、进攻方分差、回合开始类型形成分组；一起抽取得分、耗时与必要事件轨迹。
  • 对照模型：只用分差、剩余时间、主客场等信息的简单胜率模型，以及较粗的联盟回合分布。用于证明复杂度是否带来改善。
  • 后续升级：条件分类/耗时模型、球队和对手强度调整。球员阵容影响模型、战术级事件引擎不列为第一版承诺。

使用按比赛日期划分的 train/validation/test；同一比赛所有事件处于同一集合。分组范围、参考分布和平滑强度只在训练/验证集选择，锁定后评估测试集。使用固定训练截止日期的历史回放；默认不把测试期比赛结果逐场反馈进模型。记录每组样本数与回退到参考分布的原因。

3.4 第一个 what-if 参数

修改“本次模拟中某队的无得分回合概率”，例如基准 50% → 假设 45%；示例数字并非实测值。对零分与非零分回合重新分配总权重，各类内部保留经验联合分布，归一化后抽样。记录作用球队、作用时间范围、原值、新值和模型版本。样本不支持的参数或超过合法概率范围的请求应拒绝或解释支持范围。

这是明确的敏感性假设，不是“某球员上场造成胜率变化”的因果估计。节奏参数延后，避免直接压缩耗时而忽略节末、犯规和规则变化。

3.5 模拟与验证

从合格回合起点开始，以确定性随机种子批量抽样并更新状态。到节末只计入截止时刻已经发生的模拟得分事件，不把超时后的得分算进去；保留正确罚球和事件顺序。平局进入单独加时逻辑。无法处理的规则场景先标记不支持，并在最终验收前决定修复或明确缩小模型覆盖范围。

记录基准与场景的胜场数、有效模拟次数、比分/总分直方图。胜率 Monte Carlo 标准误可用 sqrt(p(1−p)/N)；例如 N=10,000、p=0.5 时约 0.5 个百分点。这只衡量抽样误差，不能表示模型参数或真实世界不确定性已经解决。比较基准与场景时使用可复现的配对随机流。

评估胜率校准、Brier score、log loss、总分/分差误差与预测区间覆盖率；以比赛为单位估计评估不确定性，避免把同场多个时点当独立比赛。模型不胜过基线时保留结果并解释，不宣称预测改善。

4. 存储、ETL 与应用流程

NBA 历史数据（原 SQLite 保留；RDS 已迁移）
    → Spark：清洗 / 回合重建 / 状态特征 / 分布估计

Streamlit 创建实验 → RDS：参数、状态、运行记录
                  → Atlas：假设说明、证据、审查文档
运行完成 → 结果入库 + 生成可追溯报告
报告 / 模型说明 / 审查文档 → 切块 → embeddings → Qdrant
Research Assistant → 检索证据 + SQL 查询精确指标 → 引用回答

4.1 Operational schema 与文档

RDS 新建独立 operational schema，建议表：experiments（一项调查）、scenarios（一版参数）、simulation_runs（一次运行）、reviews（一次审查决定）。实验状态 Open → Reviewed；运行状态 Queued → Running → Succeeded/Failed，两种状态分开。关联用户、比赛、模型和版本。运行引用不可变场景版本；修改参数生成新版本。

Atlas 复用已有集群，新增 experiment_documents 和 model_documents。前者存用户假设、来源、审查正文、修订版本；后者存模型说明、由真实计算生成的报告和已知限制。RDS 是状态和结构化参数的来源，Atlas 是文档正文的来源；用稳定 ID 关联。跨库写入使用幂等键和可重试状态，失败时显示“文档未保存”，不假装跨库事务原子完成。

4.2 Star warehouse：明确粒度

表一行代表什么指标或用途
fact_possession一个合格历史回合开始状态、得分、耗时、质量信息，关联比赛/日期/球队维度。
fact_simulation_result一个 run × 一个比赛起点 × 一个场景模拟次数、胜场数、均值/分位数、耗时；重试批次合并后唯一。
fact_simulation_histogram一个结果 × 一种指标 × 一个固定区间分差/总分分布计数，保留绘图与分析需要的分布。
fact_prediction_evaluation一个基准预测结果 × 一个评估版本实际结果、预测误差及评分。人为改变假设的场景没有真实反事实标签，不拿原赛果当其准确性证明。
dim_date / dim_game / dim_team / dim_model / dim_scenario对应日期、比赛、球队、模型版本、场景版本代理键和唯一自然键；球队作为进攻/防守的角色维度复用。

ETL 保存 batch_id、源数据版本、模型版本、运行种子、生成时间、行数和拒绝记录。先写 staging，再按唯一键合并；重复加载不得翻倍。SQL 检查维度孤儿、重复事实、计数一致性与比赛最终比分。warehouse 使用现有 RDS 的独立 schema 即可，不默认购买 Redshift。

4.3 Spark 与 AWS 路线

本地先完成小样本正确性。扩大时按比赛分区处理事件，按状态聚合；模拟按“比赛起点 × 场景 × 模拟批次”分发，每个任务批量计算并返回汇总，不把一条路径里的每个回合变成远程任务。小模型参数可广播；页面单次模拟不重新读取全部原始事件。

云端候选部署：EC2 上运行应用、后台任务与 Spark standalone；需要多机实验证据时，安排两个独立计算节点并记录实际 worker、CPU 与内存。数据从现有 RDS 通过受控 JDBC 分区读取，复用一次任务的中间缓存，避免每个模拟批次重复读库。分区数根据 RDS 承载能力决定，读取前确认源键与索引；不重新迁移原库。Spark JDBC 官方说明支持 predicates 分区，并明确提醒控制并发数据库连接。

比较同一数据、算法和模拟预算下的单机与多节点运行；分别记录读取、处理、模拟和写库耗时。报告 CPU/内存总量、wall time、吞吐量与资源时间；多机慢也如实报告。local[*] 或单机两个容器仅算单机并行。课程要求可扩展处理，并未规定必须证明单机无法完成。

应用与 Qdrant 使用 Linux 持久卷/EBS，备份与恢复可验证；向量端口不公开，用户通过应用访问。Qdrant 官方安装说明给出容器持久存储方式。配置 HTTPS、访问控制、环境变量、后台任务超时/失败重试和日志；重启后实验与向量索引可读取。S3、EMR、Kafka、Redshift 均不在第一版必需清单内。新增实例或付费模型在明确预算后才开通，本计划不执行部署。

5. RAG 的实际问题、语料与评估

RAG 服务“理解模型和查找实验依据”，不负责计算胜率，也不从几篇新闻臆测市场变动原因。语料包含人工维护的模型说明、由真实回测生成的验证报告、实际实验/审查记录，以及确实相关且保留来源的公开方法文档。文档数量跟随实际工作增长，不制造重复报告来凑规模。

  • “这个模型在最后两分钟有哪些已知限制？请引用验证报告。”
  • “当前场景为什么回退到联盟参考分布？对应模型版本怎么定义回退？”
  • “以前哪些实验审查讨论过调低零分回合概率？他们的依据是什么？”

切块保留 doc_id、revision、model_version、run_id、game_id（若适用）、created_at、source_cutoff、出处与证据片段。Qdrant 检索按版本、可见范围和问题时点过滤；精确数值从 SQL 查询，再链接到相应报告。区分“当时可以知道的内容”和“赛后模型审查”：历史赛前问答不能检索事后报告，赛后评估可以使用事后结果但明确时间。

建立至少 20 个手工核对的问题，覆盖正确检索、错误版本、无证据、历史时间过滤和精确指标查询；建议验收目标为有证据问题至少 80% 的正确证据出现在 top-5，时间/版本过滤用例全部通过，引用可定位原文，拒答用例不编造答案。阈值是项目目标，不是已达到的结果；少量文档阶段直接阅读可能更有效，要说明 RAG 的实际增益和局限。

共享接口与验证约定

build_possessions(events) 返回规范回合和拒绝记录；fit_model(possessions, split_config) 返回带训练截止日期、分组规则和版本的分布；simulate(start_state, model, scenario, n_paths, seed) 返回统一结果及直方图。批量 Spark 与页面共用同一模拟内核，避免两套算法。各模块在实施前用独立组件计划细化类型和错误契约。

每个阶段先为高影响行为写最小离线 fixture 和 unittest，再实施并验证；数据库变更在独立测试 schema/collection 检查，完成后做聚焦代码审查和分阶段提交。保留现有采集测试，新增测试不调用付费 API。执行既有 python -m unittest discover -s tests -v；集成验收另记录数据库与云端真实结果，不能用离线测试替代。

7. 最终验收与重点风险

  • □ 实际处理超过百万条真实源事件；报告过滤前后规模、赛季覆盖与来源。
  • □ 合格样本得分重建与逐节/最终比分一致；事件顺序、同时间事件、罚球、进攻篮板、节末和加时有验证证据。
  • □ 至少一个清晰定义的 what-if 参数；模拟可复现，输出含模型版本、样本支持和抽样误差说明。
  • □ 时间外测试与基线比较完成；如无提升或覆盖不足，结果如实呈现。
  • □ RDS 和 Atlas 均有来自真实应用操作的持久记录；失败与重试不产生重复事实或虚假成功状态。
  • □ Star warehouse 有真实表、明确粒度与可重复 ETL；运行结果、分布计数和维度关联一致。
  • □ Spark 实际执行，单机/多机结果和性能可复查；不声称扩容一定更快。
  • □ RAG 确实使用 embeddings 和向量数据库；引用、版本和时间过滤通过评估。
  • □ AWS URL 与重启恢复通过；报告、视频、代码和课堂展示齐备。

优先审查五类失败：跨比赛重复键导致 join 膨胀；赛后信息进入起始状态；超出样本支持的状态/参数；零时长事件和节末得分处理错误；重试导致跨库文档、运行结果与向量版本错配。分别由 M1、M2/M4、M2、M1/M2、M3/M5 的测试和验收负责。

业务成效通过小型用户任务演示记录：比较手工查看报告与平台完成“找出场景影响并定位依据”的耗时和正确性。不能把演讲中 DraftKings 的 30% 改善当作本项目结果；没有真实企业试验时，不报告节省金额或真实交易收益。
