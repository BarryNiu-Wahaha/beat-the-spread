1. 小型 Operational Database 到底是什么

Operational Database（业务操作数据库）保存用户使用系统时产生的业务记录。在这个项目中，用户是 sportsbook trading analyst。他查看赔率后创建了一项调查、写下备注、把状态改为已处理，这些记录就是 operational data。

“小型”指第一版只实现必要的几张表和一条完整流程，不是要求制造大量交易数据，也不是要求重新迁移 NBA 历史库。

举例：分析师发现一场比赛的 DraftKings moneyline 与其他博彩公司报价存在差异，在平台中点击“创建调查”；写下“需要核对报价更新时间”；检查后将状态从 open 改为 reviewed。刷新页面后，记录仍可读取。这就是一个可以演示的业务操作。

概念本项目中的含义
RDS数据库托管服务；数据库放在哪里，并不决定它是否属于 warehouse。
Operational Database支持创建、查询、更新调查与备注，维护业务状态和关联关系。
Data Warehouse通过 ETL/ELT 将源数据整理成明确粒度的事实表和维度表，支持统计分析。
ER 图表达实体及关系的设计图；画了 ER 图，不代表已经实现 operational 功能。

现有 NBA 数据是历史数据源。将其复制进 RDS，并不自动完成课程要求的 Star/Snowflake warehouse。无需先把历史数据强行转换成模拟业务交易，再重新做 warehouse。历史数据可以直接进入分析 pipeline；应用自身另外产生调查记录。

3. 第一版业务库建议只做四张表

建议表名一条记录代表什么建议保留的信息
market_events一场当前监控的比赛内部 ID、来源、外部比赛 ID、主客队、开赛时间。
investigations一次分析师调查调查 ID、比赛 ID、标题、状态、创建时间、更新时间。
investigation_notes调查中的一条备注备注 ID、调查 ID、正文、创建时间。
investigation_evidence一项调查证据引用证据 ID、调查 ID、来源类型、文档或快照 ID、可用的 URL 与证据时间。

关系是：一场比赛可以有多次调查；一次调查可以有多条备注和证据。MySQL 内部用主外键约束；引用 MongoDB 文档时保存稳定 ID，由应用检查目标是否存在。不要假设 MySQL 外键可以约束 MongoDB。

建议在现有 RDS MySQL 实例中使用独立 database，例如 nba_ops；将未来 warehouse 放入另一个 database，例如 nba_dw。这是建议命名，并未创建。既有历史库保留，避免重新迁移或覆盖。

MongoDB 继续保存赔率快照、新闻正文和后续伤病文档。当前比赛与截至 2023 年的历史比赛无法匹配时，历史映射留空，不强行关联。

4. 现在第一步具体怎么做

  1. 确定一条业务流程：从已有赔率选一场比赛，允许分析师创建调查、添加备注和修改状态。
  2. 确定表关系：为上述四张表列出字段、主键、外键、必填项和状态值，形成小型 ER 图与建表 SQL。
  3. 实现业务写入：在独立 operational database 中建表，实现创建调查、写备注、更新状态和读取列表。保存调查及初始证据时使用事务，避免只写入一半。
  4. 做最简 Streamlit 页面：读取 MongoDB 已有赔率；按同一比赛、同一市场、同一结果比较报价，显示采集及报价时间，提供“创建调查”入口。
  5. 完成一轮演示：创建调查 → 添加备注 → 改为 reviewed → 刷新页面 → 再读出记录。
第一阶段验收：页面能读出已有赔率；用户操作能写入 RDS；调查关联比赛与证据；状态和备注在刷新后保留；页面交互不触发新的外部 API 采集。

样本页面应明确显示数据日期，不能把保存的报价称为实时行情。单次快照可用于横向比较，不能据此生成赔率变化趋势。原始赔率差异与隐含概率差异也应分别标明单位。

5. 后续实施顺序

阶段要交付什么完成标准
① Operational + 最简 Dashboard四张业务表、业务写入、赔率列表、调查入口。查看赔率、创建调查、保存备注和更新状态完整跑通。
② Spark + ETL + Warehouse对历史数据进行有用途的清洗、聚合；把结果加载到事实表和维度表。明确粒度、键和质量规则；保留处理行数及日志；重复加载不无故产生重复记录。
③ Similar Game Finder赛前特征、标准化、KNN 和结果解释。先支持历史比赛之间的检索；展示相似依据及最终分差背景；无未来信息泄漏。
④ RAG Research Assistant正文切块、embedding、持久化 ChromaDB 或 Qdrant、检索和带来源回答。保留来源与时间过滤；缺乏证据时说明；用代表性问题验证检索结果。
⑤ AWS 集成与交付应用 URL、数据库连接、向量索引持久化、报告和演示。URL 可访问，重启后数据保留，团队能解释完整架构。

第①阶段跑通后可以提前做一次最小 AWS 部署，发现环境与网络问题；最终再完成整体集成。具体工期应按课程截止日和团队分工安排，这里的序号表示依赖顺序，不是已经承诺的完成日期。

Warehouse 的第一版粒度

  • fact_team_game：一支球队在一场比赛中的表现，配套球队、日期等维度。
  • fact_odds_quote：某次快照中，一场比赛、一个博彩公司、一个市场、一个结果的一条报价。
  • 调查记录后续通过 ETL 接入分析层，可统计调查数量、状态和处理时长。
NBA 历史数据 → Spark 清洗与聚合 → 比赛事实表 / 历史赛前特征 MongoDB 赔率 → ETL 展开与统一格式 → 报价事实表 RDS 调查记录 → ETL 整理 → 调查分析表 ↓ Warehouse → 分析图表 / Similar Game Finder MongoDB 新闻与报告文本 → 切块 → Embedding → 向量库 → RAG 回答

Spark 应实际处理超过百万条的 NBA 数据并产生可使用的结果，不能只在架构图里出现。历史赛前特征可以从过去比赛聚合生成；当前比赛最终得分、最终分差不能进入该场比赛的赛前特征。

6. 为什么暂时不把 Chatbot 放在第一步

聊天界面本身不能补齐 operational、Spark 和 warehouse 的课程要求。当前 10 篇 Guardian 正文足够用于小型检索试验，但不保证覆盖目标比赛、球员或伤病问题。

先做调查流程，可以让 RDS 和 MongoDB 都被实际应用使用。RAG 随后围绕具体调查问题接入；检索到的新闻或报告也能保存为调查证据，功能之间更容易连起来。

  • Guardian 新闻正文入库不代表已经完成 RAG；仍需切块、embedding、向量检索和回答引用。
  • 官方伤病状态与媒体解释分开；新闻相关性不能证明赔率变化的因果。
  • 历史 NBA 截至 2023 年，当前新闻和赔率是 2026 年样本；第一版相似比赛功能先限定历史查询。
  • 继续复用现有资源；本计划不要求新增付费服务、不启动持续采集、不要求启用 S3 或购买 Redshift。
